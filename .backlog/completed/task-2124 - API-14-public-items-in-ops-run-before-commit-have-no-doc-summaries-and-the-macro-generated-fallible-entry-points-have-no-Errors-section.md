## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**File**: `extensions/run-before-commit/src/lib.rs:7`, `extensions/run-before-commit/src/lib.rs:11`, `extensions/hook-common/src/lib.rs:118` (`impl_hook_wrappers!`)

**What**: Undocumented public API in this crate:

- hand-written, no `///` at all: `NAME` (:7), `DESCRIPTION` (:8), `SHORTNAME` (:9), `RunBeforeCommitExtension` (:11).
- generated by `ops_hook_common::impl_hook_wrappers!` and therefore public in *this* crate with whatever docs the macro carries: `HOOK_CONFIG`, `hook_config()`, `should_skip()`, `find_git_dir()`, `install_hook()` have no doc comment in the macro body (hook-common lines 118-144), so they render bare in `ops_run_before_commit`'s docs. Only `ensure_config_command` (:146) has one.
- `install_hook` and `ensure_config_command` both return `anyhow::Result` and neither has an `# Errors` section at this crate's public path, though `ops_hook_common::install_hook` documents its own.

`has_staged_files` (:112) and `SKIP_ENV_VAR` (:74) are the counter-examples — both fully documented, including `# Errors` — so the gap is inconsistency within one 120-line public surface, not a project-wide absence of doc convention.

**Why it matters**: These are the crate's entire public API and the CLI consumes all of them by path (`crates/cli/src/pre_hook_cmd.rs:10-16`). A reader of `cargo doc` sees a constant named `NAME` with no statement of what it names or that it is the on-disk command name the hook script and `.ops.toml` key both depend on, and two fallible functions with no statement of what makes them fail. The macro is the right fix site: the same gap exists identically in `ops-run-before-push`.
