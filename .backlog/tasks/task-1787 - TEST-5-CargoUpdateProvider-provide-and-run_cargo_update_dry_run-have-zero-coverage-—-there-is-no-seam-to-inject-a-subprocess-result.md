## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**File**: `extensions-rust/cargo-update/src/lib.rs:78-85` (`run_cargo_update_dry_run`), `:428-464` (`CargoUpdateProvider::provide`)

**What**: Neither public entry point is ever invoked by a test.
`grep -n "provide(" extensions-rust/cargo-update/src/tests.rs` returns nothing;
the only provider-level tests are `schema_has_expected_fields` (`tests.rs:720`)
and the two generated by `ops_extension::test_datasource_extension!`
(`tests.rs:91`), which assert only `Extension::name` and that the provider
registers under its key (`crates/extension/src/macros.rs:206-219`).

Untested behaviour in `provide`:

- the `RunError` -> `DataProviderError` mapping and its `.context(..)` wrap (`:434-436`);
- the entire non-zero-exit branch — `format_error_tail(&output.stderr, 10)`, the `{:?}` escaping, the returned message (`:444-460`);
- the success path handing `output.stderr` to `parse_update_output` (note: it parses **stderr**, not stdout — a wiring mistake no test would catch);
- the `serde_json::to_value` step and the shape of the JSON the about page consumes (`:463`).

`run_cargo_update_dry_run` has no test of any kind: nothing pins the argv
(`["update", "--dry-run"]`), the working directory, the label, or that
`CARGO_UPDATE_TIMEOUT` is the value handed to `run_cargo`.

The blocker is structural, not effort: `provide` calls the free function
`run_cargo_update_dry_run` directly, so a test cannot supply a canned
`std::process::Output`. Extracting the pure part — e.g.
`fn interpret_output(output: &Output) -> Result<serde_json::Value, DataProviderError>` —
makes every branch above testable with a hand-built `Output` and no subprocess,
which is the pattern the sibling `deps` crate already uses
(`interpret_upgrade_output` / `interpret_deny_result`).

**Why it matters**: the crate's parser is exhaustively tested (30+ cases) while
the code that decides whether the parser is called at all, and what the caller
sees when cargo fails, is not executed once. TASK-0502 exists because that
branch previously reported "no updates available" for a failed invocation —
the regression it fixed is currently unguarded. This is also what forced the
three mirror-tests filed as the TEST-25 finding on `tests.rs`; both should be
fixed by the same seam.
<!-- SECTION:DESCRIPTION:END -->
