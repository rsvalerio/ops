## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**File**: `extensions/text-fixers/src/discovery.rs:135-165` (`discover`), `:184-224` (`walk`)

**What**: walk mode filters candidates through two rules that tracked mode
never applies:

- the `SKIP_DIRS` deny-list (`.git`, `target`, `node_modules`, `dist`,
  `build`, `.venv`, `venv`, `__pycache__`, `.terraform`), via `filter_entry`
- gitignore rules, via `WalkBuilder::require_git(false)`

`discover(root, true)` returns `tracked_files(root)` filtered only by
`retain_regular_files` / `is_candidate`, which tests file *type* and nothing
else. So a file that is both tracked and inside `node_modules/`, `dist/`,
`build/`, or `.terraform/` — or one that is tracked *and* gitignored, which
git permits and which happens whenever a `.gitignore` rule is added after the
file was committed — is a candidate under `--tracked` and is rewritten, while
the default walk deliberately leaves it alone.

The module header gives the exact rationale that this breaks: "The gitignore
filter matters because the fixers rewrite files in place and exit non-zero on
change: a build artifact regenerated by an earlier step of the same
`ops verify` run (e.g. `*.tsbuildinfo`) would otherwise be 'fixed' on every
run, so verify could never pass." Under `--tracked` — the mode the pre-commit
hook actually runs in (`crates/cli/src/subcommands.rs:348-361`) — that
protection is simply absent.

The module also claims the two modes are unified: "Every candidate is filtered
through `is_candidate`, the single place that decides what a candidate is."
That is true only for the symlink/type question. `discovery/tests.rs` pins
mode agreement for symlinks
(`tracked_mode_drops_symlinks_and_agrees_with_the_walk`) and for non-UTF-8
names, but there is no test comparing the two modes over a deny-listed
directory or a gitignored path — which is why the asymmetry is invisible.

**Why it matters**: the two modes disagree about which of the user's files a
destructive in-place rewriter may touch, and the disagreement is undocumented
and untested. The mode with *fewer* protections is the one wired into the
commit hook. A repository that vendors a tracked `dist/` or `build/` directory
(checked-in generated output, a committed `vendor`-style bundle) gets it
rewritten by `ops trailing-whitespace --tracked` and left alone by
`ops trailing-whitespace` — and the non-zero exit makes the hook fail on files
the tool's own design says are out of scope.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 A decision is recorded for whether SKIP_DIRS and gitignore rules apply to tracked mode, and the module header states the answer rather than implying the modes already agree
- [ ] #2 If they should apply, tracked_files output is filtered through the same deny-list and ignore matcher as the walk
- [x] #3 If they deliberately should not, the module header says so and explains why the verify-idempotency rationale does not apply under --tracked
- [x] #4 A test compares the two modes over a tracked file inside a SKIP_DIRS directory and over a tracked-but-gitignored file, pinning whichever behaviour was chosen
<!-- AC:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Decision (AC #1): tracked mode deliberately does NOT apply SKIP_DIRS or gitignore rules; the module header now states this and the rationale — the index is the user reviewed choice of what belongs to the repository (git requires add -f to track an ignored path), and the verify-idempotency rationale does not carry over because regenerated build artifacts are untracked and thus never in git ls-files output. AC #2 therefore not applicable; AC #3 satisfied by the header text. AC #4: two new tests compare the modes over a tracked file inside dist/ (tracked_mode_keeps_a_tracked_file_inside_a_skip_dirs_directory) and a tracked-but-gitignored file staged before the rule existed (tracked_mode_keeps_a_tracked_but_gitignored_file), pinning the disagreement.
<!-- SECTION:NOTES:END -->
